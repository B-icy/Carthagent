description: Deliver a substantial software task in phases with executable acceptance evidence
argument-hint: "<task>"

Deliver this task in phases with executable evidence: $@

**Phase 1 — Inspect.** Inspect the repo and relevant installed APIs. Identify which domain skills or knowledge bases apply — check the available skills list and read the matching skill before implementing. Look for existing patterns, dependencies, and conventions you can reuse rather than reinventing. Make reasonable assumptions and proceed without asking routine preference questions. Expensive planning up front beats cheap guessing.

**Phase 2 — Plan.** Call delivery_plan before implementation (strict mode gates writes; read-only inspection remains available). The plan captures scope, acceptance criteria, complete artifact roots (product source/tests/config/docs), optional outputs (generated evidence like screenshots/build output that delivery_finish must find), implementation steps, and executable checks. Every acceptance criterion must reference a declared check id. Shape: delivery_plan({goal, assumptions[], artifacts[], outputs?[], verification?, steps[], acceptance:[{requirement, checks:[checkId...]}], checks:[{id, kind:"test"|"runtime"|"static", argv:[...], timeoutSeconds}]}). Example: checks:[{id:"test",kind:"test",argv:["node","--test","tests/app.test.mjs"],timeoutSeconds:60}], acceptance:[{requirement:"CLI counts lines and words",checks:["test"]}]. **Classify the ask:** a pure question, explanation or read-only review is informational — answer it directly, or record verification:"none" (no checks) or verification:"advisory" (optional checks whose failures are reported as context, not repaired). Keep the default verification:"required" for anything that changes product files; it enforces acceptance criteria, real non-static checks and strict finish. Use D2 for flowcharts.

**Phase 3 — Pressure-test the plan.** Before writing code, review the plan against every explicit requirement in the user's prompt. Verify uncertain APIs with installed source or a tiny executable probe. Confirm the declared checks can actually detect failure. If the plan is weak or incomplete, call delivery_revise to fix it — use {reason, patch:{...changed plan fields}}. Omitted fields stay intact; supplied arrays replace that field. Fresh evidence survives only for unchanged checks on unchanged source. Use delivery_plan for a genuinely new task after finishing or blocking the previous task; replacing an active plan is treated as a revision. The plan is a living contract, not a one-time artifact. Each revision bumps the revision shown in the plan panel.

**Phase 4 — Build.** Build a runnable vertical slice early, then complete the behavior, failure paths, tests and documentation. Mark progress with delivery_progress as each step finishes so the plan panel stays current. If development reveals a wrong assumption or a step can't be completed as planned, call delivery_revise to adjust — it keeps fresh evidence for unchanged checks on unchanged source — update steps and checks to match reality, but never silently drop original acceptance criteria. Reserve time to launch the actual product, exercise interactions, inspect screenshots if supported, and fix failures.

For medium/large repositories, map affected packages, public callers, existing conventions and baseline failures first. Use rolling-wave planning: detailed near-term slices and coarse later milestones, refined when a probe or test reveals new information. Steps may be strings or {id,title,dependsOn:[stepId...],checks:[checkId...]}. Stable IDs preserve progress through reordering. Prerequisites must be done before a dependent step starts; mapped checks must be fresh before done. Mark all structured steps done before finish. Record risky assumptions, compatibility constraints and rollback strategy; reopening a prerequisite resets downstream progress. Use kind:"regression", checks:[] for an intentionally-red regression milestone: run a focused probe via bash and record a behavioral assertion failure, not merely an import/syntax error. Keep green suites on acceptance and the later integration milestone. Run focused tests during implementation, then cross-package integration and the repository's quality gates. Newly added/remapped criteria require new assertions and new suite executions; old command evidence does not cover a newly stated requirement. Do not substitute a passing smoke test for those gates.

**Phase 5 — Verify.** Before entering the verify loop, re-check the classification once: if the ask turned out to be informational, you may replan to verification:"advisory" or "none" *only while no check has run* — after evidence exists the downgrade is refused. Otherwise use delivery_check to record evidence (it runs the declared command itself — do not pre-run the same command via bash). If checks fail, read the quoted output, repair the root cause, and rerun. For advisory plans a recorded failure is context, not a repair order; for none there are no checks. If a check failure reveals the plan was wrong, adjust the plan first, then re-verify.

**Phase 6 — Deliver.** For structured required plans, call delivery_review action="inspect", read its actual final diff and listed new files, and challenge each requirement with concrete assertions plus boundary/metamorphic probes (vary magnitudes, signs, extreme values and equivalent representations). Fix findings, rerun checks and inspect again after source edits. Call delivery_review action="record" with captureId, coverage:[{requirement,assertions}] for every criterion, probes:[commands and observed results], findings:[] and limitations:[]. Review is traceable self-report, not independent proof. Then call delivery_finish with review and honest limitations. Do not finish with only a plan or scaffold, do not claim unrun tests passed, and do not deploy externally without permission.
